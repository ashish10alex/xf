# Build a lazygit-style Dataform TUI in Go with Bubble Tea, starting with the basics

> The tool is now called `xf` (it was `dft`; `.dft/` is now `.xf/`, `DFT_*` is `XF_*`), and it also opens dbt projects. See 0002-multiple-backends-dataform-and-dbt.md. Names below are as they were when each section was written.

vscode-dataform-tools (~/vscode-dataform-tools) only works inside VS Code. A "Terminal" mockup of its Compiled Query panel (box-drawn panes, single-key actions, a streaming run log) showed that a
keyboard-driven TUI in the style of lazygit or k9s would suit the everyday loop of reading compiled SQL,
checking lineage and running an action. We will build it as a standalone Go program using Bubble Tea, the stack behind most tools in this category, so it starts instantly,
ships as a single binary and gets the polish of Bubbles (list, viewport, text input) and Lip Gloss.
It talks to Dataform only through the `dataform` CLI and does not share code with the extension.

v1 is deliberately small. Anything not listed under v1 below waits until the basics feel right.

## v1: the basics

- **Compile** the project through the shared engine (see "One engine" below), which runs `dataform compile --json` from the project root (the nearest directory above the working directory with `workflow_settings.yaml`). `c` asks the engine to recompile, and saving a file under `definitions/` or `includes/`, or `workflow_settings.yaml`, recompiles automatically (debounced), so an editor in a split such as neovim gets feedback on save. Compile errors are shown instead of crashing the program; the last good compile stays on screen, marked stale, until the project compiles cleanly again.
- **Find an action** with `/`, a palette over the panes like VS Code's quick open, rather than a list pane taking up the screen. Each action is a row labelled by its target, `schema.name` with the schema dimmed, and its type alongside. Typing fuzzy-matches the labels and highlights the matched characters. With an empty query it lists the current action, then the actions of the file open in the editor, then recently selected ones, then the rest by name, with the cursor on the second row so `/` `enter` switches back to the previous action. `enter` picks and focuses the SQL; `esc` cancels. The palette opens by itself after the first compile when nothing is selected. A query word that starts with `$` keeps one kind of action (`$view`, `$test`): each backend has the kinds its tool has, so `$snapshot` exists only in a dbt project. A query that starts with `>` lists commands instead, as in VS Code: what the keys do, findable by name and grouped by the start of their title (`View: log`), and a run of the selected action, which the title names, with each choice of dependencies and dependents. What switches something shows `on` or `off`; what doesn't apply now, such as a run of a declaration, is left out.
- **Actions pane:** every action the selected action's file defines (a table and the assertions generated from its config, say, none of them hidden), mirroring the cards at the top of the extension's Compiled Query panel. Each is a row with its type and full `project.dataset.name` (tags are left out), and under it a labelled line per fact, left out when there is none: its dry runs (`dry run`, or `full` and `incremental`) and `partition`. A name or value wider than the pane wraps under itself rather than being cut. The selected row is the action the other panes show; `j`/`k` in the pane, or `]` / `[` anywhere, move it, `enter` focuses its SQL, `u` opens its table or view in the BigQuery console (the link the language server's hover title uses; not for an operation, notebook or property graph, whose target may not exist), `y` copies its name quoted for a query, `` `project.dataset.name` ``, and `Y` the path of the file defining it, relative to the project root (`Y` again copies the absolute path). `u`, `y` and `Y` do the same for the entry under the cursor in the lineage pane. It grows to its content, stopping where the SQL would drop below 8 rows, and scrolls to keep the selection in view.
- **Dry run** each action in the Actions pane, through the engine's dry-run cache, with the BigQuery API (`jobs.insert` with `dryRun`, Application Default Credentials), in the project's `defaultProject` and `defaultLocation`, as the extension does: a table's or view's query after its pre_operations, both variants of an incremental table (a `full` and an `incremental` line, the one the SQL pane shows in full colour), an assertion's query and an operation's statements. Bytes are shown in binary units with the on-demand cost ($6.25/TiB), `≤`/`≥` when BigQuery gives a bound, and a warning instead of `0 B` when it cannot estimate. A rejected query shows BigQuery's message on its line; missing credentials show how to log in. Results are kept per query text, so only changed SQL is dry-run again; failed ones are retried after the next compile (`c`).
- **SQL pane:** the compiled query of the selected action, highlighted, with pre- and post-operations in the same scroll. For incremental tables, `i` switches between the incremental and non-incremental queries. The pane searches as vim does. `/` is the find-action palette, and the SQL pane is where it is pressed most, so `/` searches the SQL only when the pane is zoomed (`z`); the palette's `SQL: search` command zooms and starts a search from anywhere. `n`, `N`, `*` and `#` work unzoomed too. A typed query is plain text with smartcase (case counts only when it has an upper-case letter); `*` and `#` take the word under the cursor as a whole word in any case, since SQL names ignore case. A search is a motion, so it extends a `v` or `V` selection. It goes around the ends and says so. `esc` drops one thing at a time: the selection, the highlights, the zoom. The pattern and its highlights stay when another action is shown, to follow a column from one action to the next; only the last pattern is kept, and `/` `enter` repeats it. There is no `?` for a backward search, which is the help.
- **Lineage pane:** direct dependencies and dependents of the selected action. It starts collapsed to its titled border with the counts (`▸ 2 lineage · ↑2 ↓4`), as the extension collapses Data Lineage; `O` expands and collapses it, and focusing it expands it. `enter` on an entry jumps to that action and `backspace` goes back (also after a palette pick).
- **Run** the selected action with `dataform run --actions <target>` using `r`. Toggles for `--include-deps` (`d`), `--include-dependents` (`D`) and `--full-refresh` (`f`) are shown on screen, and the command's output streams into a log pane (`L` shows or hides it). Only one run at a time. `ctrl+c` cancels it gracefully (SIGINT: dataform cancels its BigQuery jobs and waits for them), a second `ctrl+c` force-kills it, and `ctrl+c` quits when nothing is running.
- **Run through the Dataform API:** *Amended 2026-09-30.* A fourth toggle, `a`, makes `r` run the selected action in GCP instead of locally, as the extension's `api` execution mode does. It starts off each session; `--run-mode api` starts it on. dft compiles the pushed branch (a compilation result with `gitCommitish` set to the current branch, no compiler overrides, like the CLI run) and creates a workflow invocation whose `includedTargets` is the selected action, with `d`, `D` and `f` as `transitiveDependenciesIncluded`, `transitiveDependentsIncluded` and `fullyRefreshIncrementalTablesEnabled`. The project is `defaultProject` and the location `defaultLocation` (`--dataform-location` overrides it, for a repository in another region than its data); the repository is the last path segment of the `origin` remote without `.git` (`--dataform-repo` overrides it); credentials are Application Default Credentials, as for dry runs. What runs is the pushed branch, not the files on disk, so when the working tree is dirty, has unpushed commits, is behind, or its branch has no remote, the log opens with a warning saying so, and the commit Dataform compiled; dft runs anyway rather than ask. A compilation result with errors stops before invoking and lists them. The run fills the same stream as `dataform run`, so the log pane and one-run-at-a-time are unchanged: the first line is the console URL (`u` in the log pane opens it in the browser, with `open` or `xdg-open`), then every few seconds dft polls the invocation and logs each action's state change (with the failure reason), until the invocation ends. `ctrl+c` asks Dataform to cancel it and keeps polling until it is cancelled; a second `ctrl+c` stops watching and leaves it to GCP. Quitting during an API run doesn't touch the invocation (it doesn't ask, as for a local run) and prints its URL on exit. The API is called over REST like BigQuery (`internal/dataformapi`, no client library), and runs stay in the TUI rather than the engine. Syncing uncommitted files into a Dataform workspace (the extension's `api_workspace` mode) and a history of invocations stay out.
- **Follow neovim:** a small plugin (`nvim/plugin/dft.lua`) says which file is active by sending a `dft/activeFile` notification through nvim's `dft lsp` client (`BufEnter` has no standard LSP message), and the engine passes it on to every attached TUI. This replaces the plugin's own Unix socket. dft selects that file's first action (the table before the assertions generated from it, say), unless one of its actions is already selected, and the palette lists the file's actions first; files without actions leave the selection alone. `F` pauses and resumes following, and `backspace` undoes a switch.
- **Side by side with neovim:** `:Dft` (in the plugin, `nvim/lua/dft.lua`) opens dft in a terminal split on the right, 40% of the width, and focuses it (only focuses it, if it is open); the layout lives only there. `dft --nvim [file ...]` replaces itself with the user's own neovim, opening the files (or the working directory, as `nvim .` does, so a file explorer that takes over directories shows) and opening the split with the focus left in the editor, as the user's config set it up: the plugin is embedded in the binary (written once per version under the user cache directory) and loaded only when the user's config hasn't (no `:Dft`), and the language server is enabled with this dft's own command only when the config hasn't enabled `dft`, so neither doubles up with an installed plugin. When a file explorer has taken over the only window (nvim-tree with the directory), an empty window is made beside it: explorers don't open files in terminal windows, so without one nvim-tree rearranged the windows to make room and moved dft to the left. Beside neovim (`$NVIM` set) dft doesn't open the palette after the first compile, as it does on its own, but shows the editor's file, or failing that the first runnable action. Run inside a neovim terminal, `dft --nvim` refuses rather than nest neovims. The dft split starts in terminal mode when entered, `<C-w>` window commands work from inside it, and it closes when dft quits.
- **Open in neovim:** `o` opens the selected action's file in the editor window beside dft (the previous window, else another normal window; a file explorer's window is replaced, as picking the file there would, since explorers such as nvim-tree keep other buffers out of their window) and focuses it; neovim restores the last cursor position, since actions carry no line. dft reaches neovim through `$NVIM`, which neovim sets in its terminals, by calling the plugin with `nvim --server $NVIM --remote-expr`, so it also works in a `:terminal dft` opened by hand. Outside neovim `o` is left out of the footer and help and says why if pressed. In the SQL pane's visual mode `o` stays "other end".
- **Full screen in neovim:** `Z` shows dft over the whole editor and again puts it back in its split (`z` still zooms a pane within dft). The plugin shows the dft buffer in a float the size of the editor, so the terminal takes the float's size, and closing it gives the split's size back; the window layout underneath is never touched. Leaving the float for another window, or `o` opening a file, closes it too, so the editor is never left hidden behind dft. Like `o`, it goes through `$NVIM`, acts on the dft window that pressed it (so a `:terminal dft` opened by hand works too), and outside neovim is left out of the footer and help.
- **Keys** follow lazygit: panes are numbered, `tab` moves between them, a footer always shows the keys for the focused pane, and `?` opens help. Navigation is vim-style (`j`/`k`, `g`/`G`).
- **Layout** is stacked: every pane full width, top to bottom (actions, lineage, a one-line run pane, SQL, log), which suits a split next to the editor and follows the extension's order. As in lazygit, the main view is `0` (SQL) and the rest are numbered down the screen: `1` actions, `2` lineage, `3` run, `4` log; `tab` visits them in that order. The SQL gets every row the other panes don't need, and at least 8 when the terminal has them: the Actions pane takes its content first, then an expanded Lineage pane its content, up to 40% of what is left; a cut-off list says how many rows are hidden (`↓ 9 more`). Names fit the width: short of room, the Run pane and the `/` palette show an action's name without its dataset, then the end of its name, and the palette fills a narrow terminal. `z` zooms the focused pane to the whole screen and `esc` restores it. Clicking a pane focuses it (and selects the clicked row); the wheel scrolls the pane under the pointer. Clicking a palette row picks it and clicking outside closes it.

## Settings: flags, config files, `dft init` and `dft config`

*Amended 2026-09-30.* The first API run against a real project failed with `Location EU is not found`: `defaultLocation` is BigQuery's multi-region, but a Dataform repository lives in a region such as `europe-west2`, and passing `--dataform-location` on every launch doesn't stick. So settings can live in files.

- **Files and precedence:** JSON, read with the standard library. Keys are flat and mirror the flags one to one: `dataformBin`, `runMode`, `dataformLocation`, `dataformRepo`, `defaultBranch`, `devCompilerOptions`. Later sources win: defaults (including `workflow_settings.yaml`'s `defaultLocation` and the `origin` remote's name) < the user file (`$XDG_CONFIG_HOME/dft/config.json`, else `~/.config/dft/config.json`, also on macOS) < `.dft/config.json` at the project root, meant to be committed so the team shares the repository and region < flags. `--config path` reads another file in place of the project file (the user file still applies), and `--config ''` reads none. A relative `dataformBin` is relative to the folder holding `.dft/` (or the named file), so `node_modules/.bin/dataform` works from any subdirectory.
- **Mistakes:** an unknown key (a typo, or a key from a newer dft) is a warning (in the TUI's footer at startup, in the log for `lsp` and `serve`) and dft carries on, so a committed file doesn't break teammates on older builds. A malformed file or a wrong value stops dft with the file and line. `dft lsp` logs it and falls back to its flags instead, since an editor can't show why its server exited.
- **Who reads them:** `dft`, `dft lsp` and `dft serve` read the same files; only `dataformBin` matters to the last two. The language server loads the files of the root the editor connects with.
- **`dft init`** writes `.dft/config.json` with the shared keys only (`dataformRepo` from the `origin` remote, `dataformLocation`), never personal ones. It finds the region by compiling for the GCP project, listing Dataform's locations there and looking for the repository in each; it asks in the terminal when it isn't found or is found in several. It refuses to replace an existing file without `--force`.\
- **`dft config`** prints each setting's value and where it came from (a flag, a file, `workflow_settings.yaml`, the `origin` remote, `PATH`, a default), which files it read, and a note when the location is a multi-region.
- **The location error** in an API run's log now says that Dataform repositories live in a region and points to `dft init`, the key and the flag.
- **Help:** `dft --help`, `-h` and `dft help` print a full reference (commands, flags as `--name`, the files and keys with an example, API runs, the main keys), and each command's `--help` prints its own usage.

## One engine: `dft serve`, shared by the TUI and `dft lsp`

*Amended 2026-09-30.* The TUI and `dft lsp` (the language server for editors, in the same binary) each compiled on save and each dry-ran the same SQL, so with nvim and the TUI open side by side every save ran `dataform compile` twice and asked BigQuery twice. There is now one engine per project, in a background `dft serve` process, and both are its clients.

- **The engine** (`internal/engine`) runs the compile and watch loop, holds the graph (or the compile errors, with the last good graph marked stale) and keeps one dry-run cache keyed by project, location and query text. It dry-runs whatever any client asks for: the actions in a TUI's Actions pane and the files open in the editor. The same SQL costs one BigQuery call, and a call in flight is shared. Diagnostics still go only to the editor's open files; the TUI shows bytes and cost.
- **`dft serve`** runs the engine and listens on a Unix socket named from a hash of the project root and a protocol version, so builds that speak different protocols never meet; each runs its own server until the old one stops. A lock file beside the socket keeps two servers starting at once from both listening. It exits a few seconds after its last client leaves, so quitting and reopening the TUI keeps the warm cache, and logs beside its socket.
- **Saved compiles:** *Amended 2026-10-01*, after the extension's PR #388. A cold `dft serve` made the TUI wait for `dataform compile` before showing anything. Now every clean compile is saved under the user cache directory (`dft/compiled/<project hash>.json`, one per project; `internal/compilecache`) with a fingerprint of its inputs, taken before the compile ran: the path, size and modification time of every file under `definitions/` and `includes/` (dotfiles aside), of `workflow_settings.yaml`, `dataform.json`, the package and lock files and `node_modules/@dataform/core/package.json`; the dataform binary, followed to its real file, with its and its package.json's size and modification time; and the UTC day, since projects compute dates in `includes/`. At start, once files are watched, the engine loads it. If the fingerprint matches, it is used as a finished compile and nothing is compiled until a file changes or `c`. If not, it is shown at once, marked `outdated` with why, while the startup compile replaces it; until then the TUI dry-runs nothing and Run Changed waits, and a compile that fails leaves it on show marked stale, as for any last good compile. A client can't tell a saved graph from a compiled one except by `saved` and `outdated` in `dft/state`; `ProtocolVersion` is 3. Output that depends on something else (the time of day, an environment variable) needs a `c`.
- **Every front end is a client** (`internal/remote`): the TUI and `dft lsp` alike never compile by themselves. A client connects to the socket, or starts `dft serve` (in its own session, so it outlives the client) when nobody is listening. `dft lsp` still handles the editor's session itself (buffers, positions, hovers, diagnostics); only compiles, the graph and dry runs come from the server. Without a dataform binary it runs an engine of its own that can't compile, as before.
- **The protocol** is JSON-RPC with LSP's framing, and none of it is standard LSP. The server sends `dft/state` when a client connects and whenever the state changes (the graph as its compile JSON, only when it is new to that client, which parses it with the same code as a local compile), and `dft/activeFile` whenever an editor reports one. Clients send `dft/recompile`, `dft/activeFile` and the requests `dft/dryRun`, whose errors keep their kind (rejected query, no credentials, timed out) so callers handle them as before, and `dft/changedActions` (see "Run Changed"). Runs stay in the TUI.
- **Takeover:** when a client loses its server, it starts another and resubscribes; the TUI keeps showing its last graph until the new server has compiled, and a dry run in flight is asked of the new server. The TUI and `dft lsp` share this code, so there is no stdio forwarding and nothing to replay. This replaces the earlier plan, in which nvim's `dft lsp` hosted the engine and a second one forwarded its stdio: taking over there meant replaying the editor's session into a new host.
- **Tests:** `internal/ui` depends on a small Engine interface (`Subscribe`, `Recompile`), and most teatest tests use a synchronous fake of it. The remote tests run real servers on Unix sockets, including takeover and idle exit; one UI test runs the TUI against a real server with a second client standing in for the editor; and the nvim plugin is run in headless neovim against the real language server.

## Run Changed: `R`

*Amended 2026-09-30, and 2026-10-01 (checking files).* A port of the extension's Run Changed (`src/changedActions.ts`, `src/utils/compiledGraphDiff.ts`), keeping its domain language: a **Changed Action** is one whose compiled output differs from the merge-base with the default branch, like dbt's `state:modified`.

- **Detection** compares compiled output, not changed files, so edits in `includes/` and `workflow_settings.yaml` count, and edits to descriptions, tags or dependencies alone don't. Each Changed Action has reasons: `new` (not in the base), `sql` (query, incremental query, pre or post operations) and `config` (type, protected, uniqueKey, bigquery options, onSchemaChange, disabled; for operations hasOutput). Absent, null, false, empty strings and empty arrays and objects compare equal, since compiles omit defaults inconsistently. Tables, operations, assertions and notebooks are compared; declarations are never run. Actions the branch removed are listed, never run. `internal/changes` holds the port with the extension's test cases, and an opt-in test (`DFT_E2E=1`) runs the real CLI on a git copy of `testdata/projects/navigation` to show that an `includes/` edit is caught.
- **The base** is the merge-base of HEAD with `origin/<defaultBranch>`, or the local branch when origin has none; dft never fetches. It is extracted with `git archive` (run from the project folder, so a monorepo's other folders stay out) into a temporary folder, the root's `node_modules` is hard-linked in when the snapshot has a `package.json`, and it is compiled with the same `dataform` binary. A base with compile errors is a failure rather than a partial graph, which would make most actions new. Compiled bases are cached in memory and under the user cache directory (`dft/changed/<project hash>/`), keyed by commit, binary and UTC day (projects compute dates in `includes/`), five per project. Failures are kept for the life of the server; `c` tries again.
- **The engine owns it.** A client's `dft/changedActions` request (`{defaultBranch, head, compile}`) names the default branch, which the engine then follows: after every good compile it diffs the new graph against the cached base, never compiling one by itself, and sends the result with `dft/state`. So a base compiled once serves every later save, survives the TUI restarting, and could serve the editor later. The TUI names its branch at startup without compiling, so a base compiled earlier the same day shows at once. When the merge-base moves to one that isn't cached (a rebase, another branch) the markers go until the next `R`. A base compile the caller stops waiting for carries on and lands in the cache. `ProtocolVersion` is 2.
- **`R`** opens an overlay at once, showing the wait while a base compiles, then lists the Changed Actions grouped by file with their reasons, and the removed ones greyed. `d`, `D`, `f` and `a` toggle there as in the Run pane; with full refresh on it warns in place, since the overlay is already the confirmation. Every file starts checked: `space` checks or unchecks the file of the row under the cursor (a file header, an action or its generated assertions; the cursor never lands on removed actions), and `x` unchecks them all when any is checked, else checks them all. Files, not actions, are checked, since a file's actions and generated assertions belong together. Unchecked files stay listed, dimmed, and stay unchecked when the list is asked for again (matched by file name; a new file starts checked) until the overlay closes. `r` (or `enter`, `y`) runs the checked ones in one run, `dataform run --actions a b …` or one workflow invocation whose `includedTargets` are all of them, and the log opens with what was compared (`1 of 2 changed actions in feat vs origin/main @ abc1234 (working tree)`). With nothing checked there is nothing to run, and the footer says so. `d` and `D` mean what they do elsewhere, so an unchecked action a checked one reads from (or that reads from it) still runs; the overlay counts those from the local graph (`⚠ d: 1 unchecked action still runs as deps`), which with `a` on may be off a little. This replaced running them all or nothing. While it asks again (`a`, `c`) the last list stays, dimmed and not runnable, so the overlay doesn't collapse and redraw. On the default branch with nothing edited it says there is nothing to compare. While the project has compile errors it refuses (`e` opens them): `dataform run` would fail on them, and the last good graph hides the latest edits.
- **API runs** compile the pushed branch, so with `a` on `R` compares `origin/<branch>` (the branch an API run compiles, whatever the local branch tracks) instead of the working tree, compiling both sides from snapshots, and working-tree compile errors don't block it. A branch origin doesn't have, or a detached HEAD, is refused with what to do. This comparison is made only on `R`; the markers always follow the working tree.
- **Markers:** the `/` palette marks Changed Actions with `●` and, with an empty query, lists them after the current action and the editor's file, before recent ones. The Actions pane adds a `changed` line (`sql, config in feat vs origin/main`).
- **Settings:** `defaultBranch` (`--default-branch`), default `main`, in the same files as the other keys.

## Column Impact: `I` and `dft impact`

*Added 2026-10-02.* A port of the extension's column impact report (PR #402: `src/columnLineage/changeImpact.ts`, `src/shared/columnLineage/impactSummary.ts`, `impactRules.ts`, `dataplexLinks.ts`, `dataplexSource.ts`), the report only: the extension's per-file column list and its interactive column trace are not ported.

- **What it checks.** The Changed Actions that build a table (tables, views, incremental tables, and operations with `hasOutput`), and the deleted tables, views and incremental tables. Each changed one's BigQuery table is read; it is dry run (the same script dft dry-runs for its cost, so the engine's dry-run cache serves both; an incremental table's full rebuild) and the dry run's schema compared with the table's: top-level columns dropped or retyped (`INTEGER` ≡ `INT64` and so on), names compared case-insensitively, as in the extension. Operations, tables with no table in BigQuery yet, and failed dry runs are listed as not checked, with why.
- **Prod Targets.** The extension compares with each action's Prod Target, compiled with `prodCompilerOptions`. dft compiles with no options, so without the key it compares with the project's defaults, which are what the extension uses when `prodCompilerOptions` is unset. A project whose defaults point at dev tables (`defaultProject: acme-dev`, prod runs with `--default-database=acme-prod`) would then compare a branch with tables built from it and find nothing. With `prodCompilerOptions` set (a team key for `.dft/config.json`, `--prod-compiler-options`), the check compiles the working tree once more with them and matches targets to actions as for dev runs (`--default-database` moves canonical targets too, so the match is mostly by dataset and name); deleted actions' prod tables are guessed from an action sharing their dataset. Each changed table is compared with, and its readers looked up at, its prod table; an action with no match is not checked. Prod runs fold into their actions as dev runs do, and the report names tables by their prod tables. The report says what it compared with, `Evaluated against: tables in <project>` and `keep every column they have in <project>`, where the extension says "production schemas" and "prod column"; a report without projects (the parity test's) keeps the extension's wording byte for byte. The options travel in the request and key the kept report; `ProtocolVersion` is 5.
- **Readers** come from Dataplex Data Lineage over REST (`internal/lineage`, `searchLinks` in the table's project and region, Application Default Credentials with the cloud-platform scope), ported from the extension's Dataplex source, downstream only: a column's links, then readers Dataplex knows only at table level and doesn't track the columns of (incremental tables always; others found by probing their first three columns), assertions left out. A reader that can't be probed counts as untracked, so it is listed rather than dropped. Readers are marked in the project or outside it, changed on the branch, "probably updated" when their new SQL no longer names the column, and "deleted here" when the branch deletes them too (assertions included); the last two count as settled, and a table with nothing unsettled reading it counts as low. Severity, sorting and the Markdown (with its collapsed Readers table per model) are a verbatim port (`internal/impact`), with the extension's test cases. Names sort with Unicode collation (`golang.org/x/text/collate`), as JavaScript's `localeCompare` does, not by bytes. An opt-in test (`DFT_EXTENSION=<checkout>`) bundles the extension's `impactSummary.ts` with its esbuild and checks hundreds of random reports, reader lists and orderings against it, byte for byte.
- **Dev runs.** Dataplex records dev runs' lineage too. The extension folds a reader that is a dev run of a project action into the action, mapping its own compile's targets (the user's compiler options) to Prod Targets. dft compiles with no options, so with `devCompilerOptions` set (a personal key, `--dev-compiler-options`) the check compiles the working tree once more with them and maps dev targets to its own by canonical target, as the extension's `buildProdTargetMap` does; the dev targets of deleted actions are guessed from an action sharing their prod dataset, the extension's `guessProdTarget` the other way round. Without the key, nothing is folded, as in the extension without dev options. The options travel in the request, and a report is kept per options.
- **The engine owns it.** `dft/columnImpact` (`{defaultBranch, head, refresh, token}`) works out the Changed Actions as `R` does (refusing on working-tree compile errors except for the pushed branch), then checks them, sending `dft/impactProgress` notifications with the request's token. A check under way is joined, not started twice, and carries on when the caller stops waiting. The last report per branch and head is kept in memory, keyed by a signature of the Changed Actions and their SQL; asked again with another signature, it comes back marked stale, and `State.ImpactSignature` lets a client see that live. Failed checks are not kept. Nothing goes to disk, since lineage moves every couple of hours. `ProtocolVersion` is 4 (5 with Prod Targets, above).
- **`I`** opens an overlay that shows progress, then the report's Markdown highlighted with chroma (what you see is what `y` copies), scrolling with `j`/`k` and panning with `h`/`l`, since its tables are wide. `c` checks again; `a` switches between the working tree and the pushed branch, as in `R`; `esc` closes it while the check carries on.
- **`dft impact`** prints the Markdown to stdout (or to a file with `--output`) and progress to stderr, always checking afresh (`refresh`), through the same `dft serve`. `--pushed` checks the pushed branch; `--fail-on critical|warning` exits 1 at that severity or worse (an unknown, a failed reader lookup, never fails it, and is reported on stderr); a check that can't be made exits 2.
- **New actions, and the default targets.** *Added 2026-10-08*, after a report on a real branch listed a model the branch adds as a changed table that "keeps every column": its author had run the branch into the dev project the report compared with. Two departures from the extension when they were made, since ported to it, with the parity test covering both.
  - An action Changed Actions marks new is reported under **New**, counted as `N new` rather than `N not checked`. With no table at its target it isn't dry run. With one it is still compared, since an existing table can have readers: among the tables at risk, marked "new on this branch", when it drops or retypes a column, else under New as "table already in X, keeps every column".
  - Nothing said that `prodCompilerOptions` was unset. A client now says so in its request (`unset`, the name of the setting when no file or flag sets it, not even to `""`), and the engine copies it onto the report it answers with, never the kept one, which serves callers either way. Reports with it say they compared with the default targets, which may be dev tables: the TUI under "against", `xf impact` on stderr, the Markdown as a last `<sub>` line. `C` and `xf cost` do the same (`unsetSetting` in the JSON), and in a dbt project for `dbtTarget` when no file, flag or `$DBT_TARGET` chooses one.
  - The first `I` or `C` of an xf in a Dataform project with it unset asks for the options. They are saved to `.xf/config.json` (`config.SetProjectKey`, which keeps the file's other keys) only once the project compiles with them, which a bare project name doesn't. "The default targets are prod" is a second choice reached with tab, saved as `""`, so a stray enter on an empty box can't silence the prompt for the team. esc checks against the defaults and asks again next session. The commands never ask.
  - `ProtocolVersion` is 13.
- **The base branch's changes.** *Added 2026-10-08*. Compared with prod, a branch was blamed for a column its base branch had dropped in a commit not yet released: true of what a release does to prod, wrong about which change does it, and nothing the branch's author can act on. When a changed table (not a new one) drops or retypes a column, the action as it is in the merge-base's compile, which Changed Actions already made (`Deps.Base`), is dry run as well; a change whose `DiffSchemas` against the same table is identical is the base's (`ColumnChange.OnBase`). It stays in the model's table with its readers, reads `DROPPED on origin/main`, sorts after the branch's own, and is low whatever reads it, so it is out of "N at risk" and `--fail-on`: the change that made it on the base was the one to gate. Only tables already at risk pay the extra dry run, which the engine's cache serves when the SQL is unchanged. No base compile, no such action there, or a failed dry run leaves the change the branch's. The one departure from the extension left; a report with no such change reads as the extension's. `ProtocolVersion` is 14.

## Columns: `S`

*Added 2026-10-07.* The SQL pane has a second view: the columns the selected action's query returns.

- **Where they come from.** The schema of the dry run the Actions pane already made for the action's cost, so the view asks BigQuery nothing. An incremental table shows the variant the SQL shows (`i`). Only the TUI has it; the engine already sends the schema with each dry run, for an editor to show later.
- **The view.** `S` swaps the pane between the SQL and the columns from any pane, without moving the focus, and the choice stays as the selection moves (it is not kept across restarts). The title reads `0 sql │ columns · …`. It is a `bubbles` table, as the run table is: the columns by name, each `RECORD` followed by the fields in it at every depth, named by their path (`items.sku`, as a query names them once the column is unnested), their types as BigQuery returns them (`INTEGER`, not `INT64`) and their modes, `NULLABLE` left blank. The border counts them.
- **Keys**, with the pane focused. The move keys move a row cursor; `y` copies the column's name and `Y` its name and type. `/` filters, where elsewhere it finds an action: a box under each of the name and the type, `tab` between them, both matched as substrings whatever their case and both required. While typing, `ctrl+n`, `ctrl+p` and the arrows still move the cursor, as in the palette. `enter` keeps the filters and returns the keys to the table; `esc` clears them. The boxes are drawn only while typing or set, and selecting another action clears them, so a leftover filter never makes a table look short. The mode has no filter.
- **Nothing to show.** A dimmed line says why: the action has nothing to dry run (a declaration, a seed), its dry run is a script's and has no schema, it is still running, or there are no dry runs here. A failed dry run shows the first line of its error and points at `e`. `/` then finds an action, as there is nothing to filter.

## Consequences

- The `dataform` CLI (an npm package) is still a prerequisite, so users still need Node, but the TUI itself does not. It should find the binary on `PATH` or through `--dataform-bin` / `$DATAFORM_BIN`, the same convention `dataform-graph` uses.
- The TUI depends on the shape of `dataform compile --json` output. Keep a few real compiled-JSON files as test fixtures, from different `@dataform/core` versions, so a format change fails a test rather than the UI.
- Once later features arrive, logic that exists in the extension will be written a second time in Go, above all Changed Action detection and the Deferral rules. The extension stays the reference: the TUI keeps its domain language (Changed Action, Deferral, Deferred Action, Stale Deferral, Proxy View, Dev Target, Prod Target) and follows the extension's ADR 0001 (defer by rewriting SQL for reads and creating Proxy Views for runs). Port each rule together with its test cases so the two implementations don't drift.
- Following Bubble Tea's model, running happens in commands that send messages back to the UI, and the engine's notifications arrive the same way. Run output is read line by line from the child process and sent as messages, so the UI never blocks on a subprocess or on the engine.
- The `dft/*` methods are a private protocol that happens to use LSP's JSON-RPC framing. Changing one means bumping the protocol version in the socket name. Until the editor's `dft lsp` restarts after `just install`, the TUI and the editor each run their own server, and work is duplicated again during that window.
- Using dft always involves a background `dft serve`, even with only nvim open: a process the user didn't start by name. It only lingers for its short grace period after the last client leaves.
