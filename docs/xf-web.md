# xf web

```bash
xf web
```

opens the same panes in your browser: actions, a target section, run, SQL with its columns and lineage, the log with its jobs and history, and every overlay (`/`, `R`, `T`, `I`, `C`, `e`, `?`). The panes stack as they do in the TUI. Every key does what it does there, the SQL pane's vim keys included, but a few. `cmd+p` (`ctrl+p` on Linux and Windows) finds a file, and `#` typed in it an action; pressed again in the open palette it moves down the list, as in VS Code ([why](adr/0014-xf-web-cmd-p-finds-files.md)), but in an app window on Linux and Windows, where ctrl+p moves up and ctrl+n down. `/` searches the focused pane as in vim (the SQL, zoomed or not, the columns or the source), so off a Mac ctrl+p moves up only in a box other than the palette and in an editor's completions ([why](adr/0005-xf-web-finds-actions-with-cmd-p.md)). ctrl+n moves down on a Mac, but on Linux and Windows a browser tab never gets it: the browser opens a new window instead, and the arrows move. An app window does get it (below). And `tab` (`shift+tab` back) goes round pane 2's `sql`, `columns` and `lineage` tabs, and `errors` when there are any, while one of them has focus, in place of `S` ([why](adr/0009-xf-web-switches-sql-and-columns-with-tab.md)); `O` shows the `lineage` tab, and again goes back to the SQL ([why](adr/0022-xf-web-pane-2-has-a-target-section.md)). The log pane's tabs (log, jobs, history and the terminal) go round with `⌥⌘→` (`⌥⌘←` back; `ctrl+alt+→/←` on Linux and Windows), from inside the terminal too, where `tab` is the shell's ([why](adr/0023-xf-web-log-pane-tabs-go-round-with-cmd-option-arrows.md)).md)). And `c` goes round pane 2's `sql`, `columns` and `lineage` tabs from any pane but the source and the file tree, and gives that section the keys, so `z` zooms it and `j`/`k` move through the columns (or the lineage); it doesn't compile: `cmd+s` (`ctrl+s` on Linux and Windows) does, from anywhere, saving the source pane first ([why](adr/0017-xf-web-shows-columns-with-c.md)). And `ctrl+,` (on a Mac too, where `cmd+,` is the browser's) opens and closes the settings page from anywhere, the editors included, in place of `,`. You can click, double-click and scroll as well. Drag the line between two panes to resize them; a double-click on it gives the pane its own size back, and the sizes are kept in your browser per project. It takes the same flags as `xf`; outside any project it lists the projects xf has opened before, and typing searches them by name, path or tool; `ctrl+y` copies the full path of the project (or folder) under the cursor, since `y` would type into the search.

xf web listens on 127.0.0.1 only, on a free port (`--port` picks one), and opens the URL it prints (`--no-open` just prints it). `--app`, or `webBrowser` set to `app` in your user config, opens it in an app window of Chrome, Edge or Chromium (the first found; in WSL, Windows's own, from `/mnt/c`, unless WSL can't run Windows programs, when xf web says how to fix that and tries a Linux one) instead of a tab: a window with no tabs or address bar, which gets ctrl+n (down, as in the TUI), so on Linux and Windows ctrl+n moves there as it does on a Mac. `webBrowser` can name the browser instead, by path or name (`msedge`, `/Applications/Chromium.app`); with none found, or when the browser won't start, xf web says so and opens a tab. A link the app window opens (a merge request, a pipeline, a BigQuery job) goes to the system's browser, which Chrome gives to the profile it used last, opening a new window when that profile has none; set `webBrowserProfile` to a profile directory (`Profile 1`; chrome://version names it, at the end of *Profile Path*) and the app window opens in that profile, and its links open as tabs of that profile's window. It answers only its own page: a request must name 127.0.0.1 or localhost, and the browser's `Origin` and `Sec-Fetch-Site` headers must say it came from xf web's page, or that you opened it, so another site can't drive it. There is no token on this machine, so a reload, a restart on the same `--port`, and several xf webs at once all keep working. Runs belong to xf web, not to a tab: a run carries on when you close the tab, every open tab shows it, and reloading picks it up again. Each tab has its own selection. `esc` in pane 2 (once a zoomed pane is unzoomed) asks to close the project, and `y` (or `enter`) closes it, cancelling a local run as `q` does in the TUI, and every open tab goes back to the list of projects, where you can open another; any other key stays. `q` and `ctrl+c` don't close it. The Scratch view, the settings page and the Checks page ask the same way before going back, and their × or ← in the top bar goes at once. Closing any overlay or page (the palette, whether its pick ran or not, help, the Scratch view, the settings) gives the keys back to the source pane (in vim's normal mode with `vimMode` on, else ready to type), unless what ran gave them to the file tree, Search or the log. In the lineage tab `enter` does nothing; a double-click jumps. To open one xf hasn't opened before, type its path in the list's search (`~/…` or `/…`): the folders it completes to are listed (tab completes, or tap a folder to go into it), each one that is the root of a Dataform or dbt project labelled with its tool, and enter opens it. Enter on a folder that is no project finds the projects in it instead, as `xf search` does (the list's *find the projects in a folder* link starts at `~/`, and so does the button when xf knows no projects yet): they list as the search finds them, each ticked unless xf lists it already; `space` (or a click) ticks and unticks one, `ctrl+a` ticks all or none, and enter (or *Add*) adds the ticked ones to the list, not opened yet, marked new. `esc` stops a search still going, keeping what it found, and again goes back to the folder. Started outside any project with none opened yet, xf web starts on that list. To reach xf web from another device on your tailnet, proxy to it with `tailscale serve` and pass the Tailscale name to `--allow-host`: the URL xf web prints then carries a token, which every request needs, from this machine too. A request a proxy forwarded without `--allow-host` (one with `X-Forwarded-For` or `Forwarded`) is turned away. ctrl+c in the terminal, or in the list of projects, stops xf web. So does closing every browser window: once the last one has been closed for 45 seconds, xf web (and `xf scratch`) stops by itself, and opening the URL again before then carries on (a reload is back well within that). A run going holds it off; the 45 seconds start when the run ends. The terminal says when it is counting down and when it stops. Set `webAutoExitSeconds` in your user config, or `--web-auto-exit-seconds`, to change the wait; `0` turns it off. With `--allow-host` it is off unless one of those sets it, as a phone's browser drops the page's stream when you switch apps. `o` opens a file in the editor connected through `xf lsp`, or else with your editor setting. A terminal editor (such as `nvim` from `$EDITOR`) can't open from a browser, so `o` then lets you pick one with a window (VS Code, Cursor, Zed and so on, or any command) and saves it to your config, or to the project's `.xf/config.json` if you choose; `>` *Open: choose the editor o uses* changes it at any time.

**Back to xf web from Raycast (Mac).** An app window is a Chrome window, not an app, so Raycast's search doesn't list it. [`scripts/raycast/xf.sh`](../scripts/raycast/xf.sh) is a Raycast script command that does: typing `xf` in Raycast brings the xf web window you used last to the front (the project list or a project, skipping windows whose xf web has stopped), or starts `xf web --app` when none is open. To set it up:

1. Copy it into a folder of Raycast scripts and make it executable (`chmod +x xf.sh`). In Raycast, Settings → Extensions → **+** → *Add Script Directory* adds that folder.
2. Run `xf` in Raycast once and click **Allow** when macOS asks whether Raycast may control Google Chrome. If it doesn't ask, turn on Google Chrome under Raycast in System Settings → Privacy & Security → Automation; if Raycast isn't listed there, `tccutil reset AppleEvents com.raycast.macos` makes macOS ask again.
3. Optionally, give the `xf` command a hotkey in Raycast's settings.

It looks only at Google Chrome's windows, which is what `--app` opens when Chrome is installed (it tries Chrome before Edge and Chromium). Raycast runs scripts with a bare `PATH`, so the script takes your login shell's (zsh) before starting xf web; without it, xf web can't find `dataform`. It logs what it saw and did to `~/Library/Logs/xf-raycast.log`. To keep two xf builds apart (a release and a nightly, say), set `bins=` at the top of the script, or give a second script command `XF_BINS=~/go/bin/xf exec "$(dirname "$0")/xf.sh"`: each then brings forward only windows whose xf web runs one of its binaries, and starts the first of them that exists.

**xf as a Mac app (xf web).** Chrome can install the page as an app of its own, `xf.app`, with xf's icon, in the Dock, ⌘Tab, Spotlight and Raycast. Chrome's menu, **Cast, save and share → Install page as app** (or the install icon in the address bar), does it. The app is only a window onto `http://127.0.0.1:<port>` and cannot start xf web, so it needs two things:

1. **A fixed port.** An install belongs to one address, and xf web otherwise picks a free port each run, so run it with `--port 7777` (the page you install from must be that address).
2. **An xf web that is already running.** [`scripts/launchd/xf-web-agent.sh`](../scripts/launchd/xf-web-agent.sh) installs a launchd agent that keeps `xf web --port 7777 --no-open` running from your login, and starts it again if it stops:

```bash
scripts/launchd/xf-web-agent.sh install        # or: install 8080 for another port
```

Then open `http://127.0.0.1:7777` in Chrome and install the page. From then on, opening `xf` anywhere starts at once, with nothing to launch first. The agent turns the 45s auto-exit off (`--web-auto-exit-seconds 0`), takes your login shell's `PATH` so xf web finds `dataform`, `gcloud` and `dbt`, starts in your home folder (so it opens on the list of projects), and logs to `~/Library/Logs/xf-web.log`. `print` shows the plist without installing it and `uninstall` stops and removes the agent. `just install` restarts the agent on the new binary (by hand: `launchctl kickstart -k gui/$(id -u)/dev.xf.web`); re-run `install` if the path of `xf` changed. With the agent installed, a Raycast `xf` script command and the installed app both show up as `xf`; keep one of them (the app brings its own window forward, the script finds a Chrome `--app` window).

**Browser windows (xf web only).** With xf web open in more than one tab or window of a browser, the status line counts them (`⧉ 2 windows`). A click on the count, or `>` *View: browser windows*, lists them, oldest first, each with what it shows (an action, the Scratch view, the projects); `enter` or a window's number brings that one forward. Browsers seldom let a page bring another tab forward, so when yours refuses, that tab's title flashes `●` until you look at it, and the page you asked from says so. The windows find each other inside the browser alone: xf web knows nothing of what each one shows, and the windows of another browser or another device aren't counted.

**Compile errors (xf web only).** When a compile fails, the errors take the compiled SQL's place in pane 2, in an `errors` tab beside `sql (stale)` (the last good compile's) and `columns`; the page doesn't cover your work with an overlay. They are grouped as syntax / root errors (open: they usually cause the rest), unresolved references and missing dependencies, with the code a syntax error quotes, the file and line, how long the failed compile took and the binary that ran it. `e` focuses the tab, `j`/`k` move, `enter` opens a group or takes the source pane to the error's line with the editor's keys (`ctrl+o` comes back), `y` copies the errors and `tab` goes on to the stale SQL and the columns. The tab goes once the project compiles. With no compile errors, `e` shows the dry run errors as before.

**Without the Dataform CLI (xf web only).** When `dataform` isn't on your `PATH` (and no `--dataform-bin`, `$DATAFORM_BIN` or `dataformBin` names one), xf web still opens a Dataform project, so you can read and edit its files, search them and use source control; the TUI and the other commands stop and say how to install it, as before. The compile fails, so pane 2 opens on its errors tab, and above the error it shows the command that installs the CLI, `npm i -g @dataform/cli`. `enter` on that row, or its **run in terminal** button, types the command into the log pane's terminal tab, runs it and shows the tab; **copy** copies it (where there is no terminal tab, on Windows, `enter` copies it). Once the command ends and the terminal is back at its prompt, xf web finds `dataform` and compiles again by itself; after installing it elsewhere, `cmd+s` (`ctrl+s`) compiles. xf web finds the CLI on the `PATH` it started with, which a global npm install reaches when it uses the same Node: with nvm, switching the default Node to one without the CLI is a common way to lose it.

**What a compile adds to the names (xf web only).** Pane 2 has a **target** section between the actions and the SQL, open until you fold it with its caret (kept per project in your browser). In a Dataform project it has the table prefix, schema suffix and database suffix Dataform adds to the name of every table, dataset and GCP project it builds, joined with an underscore: a schema suffix `ashish` builds `xf_example` into `xf_example_ashish`. They are the settings `tablePrefix`, `schemaSuffix` and `databaseSuffix` (`--table-prefix`, `--schema-suffix`, `--database-suffix`), which xf passes to `dataform compile`, to `dataform run` and to the Dataform API's compile of an API run, so a run builds the tables the SQL names; unset, `workflow_settings.yaml`'s `namePrefix`, `datasetSuffix` and `projectSuffix` apply, as in any compile. Type in a field and press `enter` (or leave it): the value is saved, and the project reopens to compile with it, keeping the action you were on; `esc` puts the field back, and an emptied field takes the key out. The section saves to the file that already sets them, else to `.xf/config.json`, which the whole team shares once committed; to keep them in your own config, for every project, set them on the settings page's Global tab. In a dbt project the section lists the targets of the profile in `profiles.yml` (`$DBT_PROFILES_DIR`'s, the project's or `~/.dbt`'s), with the project and dataset each builds into: picking one sets `dbtTarget` and reopens the project, and picking the profile's default takes the key out. dbt has no prefix or suffix of its own; its target names the datasets. The settings page edits the same keys. See [ADR 0022](adr/0022-xf-web-pane-2-has-a-target-section.md).

**A file's declarations (xf web only).** A file that declares only external tables, two or more (a `sources.js` of `declare()`s, a dbt `sources.yml`), lists them in a table in the Actions pane, in the order the file names them, with when the selected one's table was last updated (only the selected declaration is looked up; a row keeps what an earlier selection found). Moving the source pane's cursor onto a name selects its row; a click on a row puts the cursor on its name, and `j`/`k` move through the rows without moving the cursor. Any declaration or source shows its table's columns, from BigQuery, in pane 2's columns tab and opens on it; a declared view opens on its SQL instead, as BigQuery has it. A name a loop builds has no line to go to, so its row comes last, dim. The box above the rows filters them, the caret folds the table away (kept in your browser), and the row under the mouse has buttons to copy its name, open it in the BigQuery console, and preview it: a `SELECT * … LIMIT 100` in a new scratch, which waits for you to run it. See [ADR 0015](adr/0015-xf-web-lists-a-files-declarations-in-a-table.md).

**Scratch queries (xf web only).** `s` on a model makes a scratch query from it: its compiled SQL, or a `SELECT` of the columns of the table it built (one to a line; the table must exist). The scratch is a file, `.xf/tmp/scratch_<id>.sql`, whose first line says the model, project and location it runs in; `.xf/tmp/` ignores itself in git. `>` *Scratch: go to last query* goes back to the scratch you last had open (else the one edited last), with the keys in its editor. The Scratch view lists your scratches beside a vim-keyed SQL editor (`ctrl+w` leaves it; `:w` saves, and it saves as you type). `ctrl+q` goes back to the project at once (it saves first), from the editor too; `esc` leaves nothing, so vim's normal mode keeps it. A click on the project's name in the top bar goes back too. Its other ctrl keys are vim's (`ctrl+v` selects a block, `ctrl+d` scrolls half a page), not the browser's or a Mac's emacs keys, and yanks, deletes and pastes share the system clipboard, as with vim's `clipboard=unnamedplus` (where the browser allows it: on localhost, not plain http). `cmd+enter` (`ctrl+enter` elsewhere) runs the selection, or the whole file (not a `ctrl+v` block), as a real BigQuery job labelled `xf-scratch`, billed to the project in the first line (else your credentials' quota project). `cmd+shift+p` (`ctrl+shift+p` elsewhere) opens the palette on Scratch's own commands, from the editor too: run or cancel, a new or deleted scratch, its project or location, *Format*, refreshing what is known of tables, the recent results, the result's CSV, its job in BigQuery, clearing filters or sort, copying a cell or row, the scratch list and results, the theme, the settings, switching project and going back. Cancelled, it gives the keys back to where they were.

While you edit, a dry run shows what the query would scan; it never blocks a run. It turns amber at 20 GiB and red at 50 GiB, where running asks first; any statement that isn't a `SELECT` (DML, DDL, scripts) asks too. Set `scratchWarnGB` and `scratchConfirmGB` in `.xf/config.json` to change the sizes. Results page in from BigQuery 500 rows at a time as you scroll; INT64, NUMERIC and BIGNUMERIC keep every digit, TIMESTAMPs show microseconds, and STRUCT, ARRAY, JSON, RANGE, GEOGRAPHY, INTERVAL and BYTES have their own cells (click one for a tree). A script shows its statements; pick one to see its rows. The `SQL` tab beside `result` shows the SQL the job ran (the selection, when a selection ran), read only, to search and copy from with vim's keys. `cmd+j` hides the results and gives the keys back to the editor, in normal mode. `ctrl+c` cancels a running job, `export CSV` streams every row of the result, and the `job` link opens it in the BigQuery console. Results are never written to disk.

**Recent results.** xf keeps the last 5 runs that returned rows, across your scratches, so you can go back to them: opening a scratch shows its latest one, and `h` (or `◷ recent` in the toolbar) lists all 5, newest first; `j`/`k` and `enter`, or a number, opens one, with its filters, sorts, search of all rows and CSV export as after a run. What is kept is each run's BigQuery job (its id, the SQL that ran, when, and how many rows), in `runs.json` beside the scratches (`.xf/tmp/runs.json`, or `tmp/runs.json` in xf's user config folder for `xf scratch` outside a project); the rows are read again from BigQuery, which keeps a query's result for about 24 hours and doesn't bill reading it. After that the result is gone, and the list marks it `expired`: run the query again. Deleting a scratch forgets its runs.

**More in the Scratch view.** Every column of the results has a filter box: type `uk` under `country` to keep the loaded rows whose country holds it (any case; several boxes combine, and nested values match their JSON). A banner says how many of the loaded rows match. While only some of the rows are loaded, a pause in typing searches every row in BigQuery, over the temporary table that holds the result (`enter` in a filter searches at once); above the same 20/50 GiB sizes it waits for `search all N rows` and asks first, and its bytes billed show. Click a column's name to sort it (ascending, descending, off; NULLs first, as BigQuery orders): the loaded rows sort at once, keeping INT64 and NUMERIC exact, and `sort all N rows` has BigQuery order every row, together with any filters, in the same query. BigQuery can't order STRUCT, ARRAY, JSON, GEOGRAPHY, INTERVAL or RANGE columns, so those don't sort. In the editor, table and column names complete as you type (`ctrl+space` asks): the project's own models first, then datasets and tables from BigQuery as you type `project.` or `dataset.`, and columns of the tables the query reads, alias-aware (`o.` lists `orders`' columns). A column several of those tables have is offered once, in the first table's spelling, with how many tables have it and their types (`INTEGER/STRING · 3 tables`); its info lists them. Every other word in the editor completes too, so a CTE's columns and aliases do once they are written; table names complete after `FROM` and `JOIN`, and in statements that name a table, such as `DROP TABLE`, `TRUNCATE TABLE`, `ALTER TABLE`, `INSERT INTO`, `UPDATE`, `DELETE` and `MERGE INTO … USING`; after `FROM` or `JOIN` the statement's CTEs come first. When BigQuery names a place in an error (`[2:29]`), from the dry run or a run, that spot is underlined in the editor and its line tinted, with the message at the end of the line, as Error Lens shows it. Hover a table name for its description, columns, partitioning, size and when it changed, with the model's own description. xf keeps what BigQuery says for 5 minutes, and forgets it when a scratch runs a CREATE, ALTER or DROP; `↻` or `:refresh` forgets it at once. The project and location a scratch runs in sit in its toolbar, and change the first line of the file.

`xf scratch` opens xf web on a new empty scratch (its file is made when you first type). In a project it works as above; anywhere else it is the editor alone, billed to `--project` and `--location`, else your credentials' quota project, and its scratches are in `tmp` in xf's user config folder (`~/.config/xf`, or `%AppData%\xf` on Windows).

**The dependency inspector (xf web only).** To follow one key (an order id, a date) through every table a model reads, and find where its rows go missing or wrong, `>` *Dependency inspector* in the palette opens a page on the selected model, as the Dataform Tools extension's Dependency Inspector does, for dbt projects too. It lists the model and what it reads, then what that reads, to the depth set at the top (3 at first, up to 20), leaving out assertions and tests; a model with no table of its own (a dbt ephemeral model, an operation with no output) gets no row, but what it reads does. Type a filter (`order_id = 'A1'`) and every row's query is `SELECT * FROM <table> WHERE <filter>`; untick *apply to all* to give each row its own. Each row dry runs (its button, or `enter` in its filter box) and runs, and *Dry run all* and *Run all* do the ticked rows. *Run all* always dry runs them first and asks, with what they scan and cost, marking any with no filter as a full scan; a single row with no filter asks too. At most 4 queries run at once, labelled `xf-inspector` and billed to the Dataform project's `defaultProject`, else your credentials' quota project; `ctrl+c` cancels them. They are xf web's, so leaving the page or reloading leaves them running. The box beside the tabs searches the tables by name or table, showing only those that have it in the rows and fading the rest in the graph; the header's tick then ticks only those (`esc` in the box clears it); *ticked only* beside it shows just the ticked rows. *+ add table* adds any other table of the project, picked as the palette picks an action, as a row marked `+` (and a node right of the model); it is kept with the model's page and its presets, and *remove* takes it off. Pasting a filter (a list of ids from a spreadsheet, say) tidies its spaces and tabs outside quotes, and so does leaving the global box; the global box wraps a long filter over up to five lines, and `shift+enter` in a filter box starts a new line. Above the result, the selected row's query shows highlighted as you type its filter, with its dry run's error in full when it fails. The result's ‹ › (or `⌥⌘←/→`, `ctrl+alt+←/→` off a Mac) go round the results of the rows that have run. `z` zooms the section you last clicked (the rows or graph, the result, the schema) to fill the page, as it zooms a pane; `z` or `esc` puts the rest back. Click a row (or a table in the `graph` tab, which `tab` shows) to see its result below, in the Scratch view's grid with its column filters; a row also opens its table's schema at the side, its query in a new scratch, its table in BigQuery or its file, and copies its query. With defer to prod on, an upstream row reads what its dry run would, prod's table when it isn't built in dev, and says `→ prod`; the model itself is always read from dev. What you typed and each row's last job are kept with the project's session, so the page comes back as you left it, reading its results again from BigQuery's copy of them (kept about a day). *Save* keeps the filters as a preset of the model, with the description beside them; *Save as new* adds another, and the preset menu loads or deletes one. Opening a model loads its latest. Leaving the page keeps it as it was, its search, dry runs and results too, until xf web quits or the tab closes: the palette's *Dependency inspector: go back to …* returns to it, a reload opens it again, and each model the page showed keeps its own. Presets are yours, not your team's: they are in `.xf/inspector/filters.json` at the main checkout's git root, which git ignores, shared by every worktree of the repository, and keyed by each action's name before dev settings, so a schema suffix, a table prefix or a dbt target doesn't lose them. `ctrl+q` goes back. See [ADR 0033](adr/0033-xf-web-inspects-a-models-upstream-tables.md).

**Settings (xf web only).** The gear at the foot of the rail (below), or `ctrl+,`, opens the settings page. It has two tabs, `o` and `s` switch between them, and it opens on the one it showed last. The **Overview** is the project info that `,` shows in the TUI, read-only: a line on top says how things stand (the tool and its version, the Google sign-in, the branch and what it compares with, the editor), then each section lists its labels and values, in two columns on a wide window. A click on a path copies it, and `r` reads it all again. Outside a project it is **Tools & sign-in**: the tools xf found and the Google accounts. The **Settings** are every key xf knows (those of the project's tool), grouped into Running, Tool, Editor & look and Scratch & source, with what each does. The **Global** scope edits your user config (`~/.config/xf/config.json`), the **Project** scope the project's `.xf/config.json`, which wins over it, and the **Vim** section the keys of the editor's own vim commands (in your user config: `vimNextHunk` `]g`, `vimPrevHunk` `[g`, `vimUndoHunk` `guh`, `vimStageHunk` `gsh`, `vimNextError` `]e`, `vimPrevError` `[e`, `vimHover` `K`, `vimDefinition` `gd`, `vimMenu` `gm`, `vimBufferPrev` `<leader>[`, `vimBufferNext` `<leader>]`, `vimBuffers` `<leader>b`, `vimBufferDelete` `<leader>x`, `vimFiles` `<leader>f`, `vimFormat` (no key unless you set one, e.g. `<leader>=`; see Formatting SQL), and `vimLeader` `<Space>`, which `<leader>` stands for), written as vim writes keys (`]c`, `<C-k>`), no two the same; each key says the value in use and where it comes from (a file, a flag given to xf web, or the default). A field saves on its own when you press enter, leave it or pick a choice, with the check the file's value gets, and **reset** (`x`) takes the key out of the file. The keys xf web reads as it goes (`sourceAutosaveMs`, the scratch sizes, `editor`, `theme`, `webTheme`, `webThemeLight`, `webThemeDark`, `webAutoExitSeconds`, `vimMode`, the vim keys) apply at once, in every open tab; the rest apply when the project reopens, which a banner offers (**Reopen now**, `R`). The TUI and `xf lsp` read the same files, so a change there applies to them the next time they open the project (`theme` changes open TUIs at once). Each setting shows its field on the right and, under it, where its value comes from; a field set in no file shows the value in use, dimmed. A green bar marks a setting the file sets, with its default and **reset**. **Changed** in the sidebar (`c`) shows only those. On the list of projects the gear's Settings edit the Global file alone. See [ADR 0019](adr/0019-xf-web-settings-page-has-an-overview.md).

**Vim mode (xf web only).** xf web's editors (the source pane, Scratch, the commit message box, the settings' JSON, a difference) have the usual editor keys, as VS Code's, unless `vimMode` is `true` in your user config (Settings, Vim, at the top; it applies at once, in every open tab). Without vim: `esc` closes what is open (the completions, a card, the find panel, extra cursors, a selection) one press at a time, and with nothing open does nothing, as VS Code's: `ctrl+w` leaves the editor; `/` in the source pane opens the find panel, as `cmd+f` does; `cmd+s` (`ctrl+s`) saves, `cmd+z` undoes, and `ctrl+o` and `ctrl+i` still go back and forward through the jump list. `ctrl+shift+↑` and `ctrl+shift+↓` (ctrl on a Mac too) add a cursor on the line above the top one or below the bottom one, at the same column, as VS Code's add cursor above and below do, so what you type goes to every line; `esc` leaves one cursor again. What vim's keys and ex commands do has a place in the palette's `>` commands: *Go to: next git change in file* and *previous* (`]g`, `[g`), *Go to: next error in file* and *previous* (`]e`, `[e`), *Go to: file named under the cursor* (`gf`), *Go to: the file before* (`ctrl+^`), *Buffers: next buffer*, *previous buffer* and *remove the buffer shown*, and *File: discard unsaved changes* (`:e!`); the source pane's right-click menu has the next and previous change and error too. With autosave on, the countdown starts at each keystroke rather than on leaving insert mode. The SQL pane's own vim keys (`h`/`j`/`k`/`l`, `v`, `y`, `/`) and the panes' `j`/`k` stay either way. The rest of this page writes the vim keys. See [ADR 0034](adr/0034-xf-web-editors-have-vim-keys-only-with-vim-mode.md).

**Editing the source (xf web only).** `E` shows the selected action's file (`.sqlx`, `.js`, or a dbt model's `.sql`) in pane `5`, beside its compiled SQL; on a phone it takes the compiled SQL's place. `enter` gives it the keys, in the same vim-keyed editor as the Scratch view, and `ctrl+w` (or `:q`) gives them back. `:w` (`cmd+s`, `ctrl+s`) saves it, keeping its line endings and byte-order mark, and the compile that follows updates the compiled SQL beside it; `:e!` drops your changes. `.sqlx` is coloured as the Dataform Tools extension colours it, with the JavaScript in `config { }`, `js { }` and `${ }` coloured as JavaScript. After a `$` it completes `${ref("…")}` from the project's actions, by the start of any part of a name or of a few of its parts in order (`$0300_ROI` finds `0300_PROMOTIONS_DATA_ROI`, as Scratch finds tables), and in a config's `dependencies` and `tags` their names (in a dbt model: refs, sources and macros), where a config key goes the keys its action type takes (`bigquery { }` gets `partitionBy`, `clusterBy`, …; `assertions { }` gets `uniqueKey`, `nonNull`, …), and in a `type`, `onSchemaChange` or `incrementalStrategy` string its values, and anywhere in the SQL the columns of the tables the file refers to, each name once (after `alias.`, that table's). Hovering a config key (or `K` on it) shows what it does, the values it takes and the action types that read it, and says so when the config's own type doesn't; xf lsp shows the same hover. `tab` or `enter` takes the completion in focus, as VS Code's does (in the Scratch editor too). In a `.sqlx` file's SQL (not its `config { }`, `js { }` or `${ }`), BigQuery's functions complete below the columns, as snippets whose arguments `tab` moves through, and an argument of fixed values (`DATE_TRUNC`'s `DAY`, `WEEK`, …) offers them alone; the function's signatures show above a call as you type its arguments, with the one you are at in bold. `K` on a ref shows its table's card, on a function its signatures, what it does and a link to BigQuery's docs, and on an includes name in the JavaScript (`constants.START_DATE` in a `${ }`, `config { }`, `js { }` or a `.js` file) its declaration as `includes/constants.js` writes it (a value's whole statement, a function's signature), the comment above it and a link to its line; the mouse shows the same cards. A card lists a record's fields under it, indented, with their types (an `ARRAY<STRUCT>`'s too). The card `K` shows has the keys, its frame lit (the context menu's **Show Card** too, and a card the mouse showed once you click in it): `f` filters a table's columns by name or description as you type, `esc` or `enter` going back to the card with the filter kept; `u` opens the table or view in the BigQuery console; `y` copies its full name, back-quoted, as **⧉ name** does; `j`/`k` (the arrows, `ctrl+d`/`ctrl+u`, `g`/`G`) scroll it; and `esc`, `q` or `K` close it and give the keys back to the editor. The includes card reads that one file when asked, so it costs nothing while you type. `gd` goes to the definition of what is under the cursor, as an editor's go-to-definition with `xf lsp` does, and `cmd+click` (`ctrl+click` off a Mac) to that of what is under the mouse: on a ref the pane shows that action's file with the cursor on it, on an includes name (`constants.START_DATE`) the pane shows the includes file with the cursor on its declaration, and on a CTE's name the cursor moves to the CTE. `ctrl+o` goes back to where you were, from file to file, and `ctrl+i` forward again, through gd's jumps and vim's own (`G`, `gg`, `/`, `n`, `%`), one place per line as in vim; outside the editor, `backspace` goes back to the action before a gd. The files the pane has shown are its buffers, as vim's, each with a number it keeps: `<leader>]` and `<leader>[` (`:bn`, `:bp`; the leader is Space unless `vimLeader` says otherwise) go to the next and previous one, wrapping around, and `<leader>b` (`:ls`, or **Buffers: show open buffers** in the palette's `>` commands) lists them to type into and pick from, `%` marking the file shown and `#` the one before; `:b 3` or `:b orders` goes to one, and `:bd` (`<leader>x`, or `del` in the list) removes one. `<leader>f` finds a file to open, as the palette's `cmd+p` does. Going to a buffer saves unsaved changes first (a save the file's changes on disk refuse keeps you where you are), selects the action it last showed, and leaves the jump list alone; a buffer whose file is gone is dropped. The list is kept with the project's session. See [ADR 0012](adr/0012-xf-web-source-pane-has-buffers.md). A definition in a file that is no action's (an include, a dbt macro) opens there too. A project opens again on the file it showed last, also in a new tab or after xf web restarts: the action you were on, or a file that is no action's (an include, the README) while it is still there; one deleted since leaves the action you were on before it. As in vim, `gf` opens the file named under the cursor (or after it on the line), any file of the project: the name is looked for beside the file shown, then from the project's root, as written and then with `.js`, `.sqlx`, `.sql`, `.py`, `.yaml`, `.yml`, `.json` or `.md` added, so `require("includes/constants")` opens `includes/constants.js`; `gF` opens it at the line written after the name (`file.sqlx:12`), and `ctrl+o` comes back. `gc` comments lines out, or back in when they are all commented already, as vim-commentary's does: `gcc` the line, `gc` and a motion its lines (`gcj`, `gcip`), and in visual mode the selection; `.` repeats it and `u` undoes it. `cmd+/` (`ctrl+/` off a Mac) does the same to the selection's lines, as VS Code's does, in insert mode too. A `.sqlx` or `.sql` file (and the Scratch editor) comments out with `--`, a `.js` file and a `.sqlx` file's `config { }` and `js { }` with `//`, a `.py` file with `#`; lines commented with `--`, `#` or one `/* */` around them come back in. In insert mode, `ctrl+x ctrl+f` completes a file name, as vim's does: the names in the folder typed so far, from the project's root (from the file's folder after `./` or `../`), names starting with a dot only after a dot; `ctrl+n` and `ctrl+p` move through them, and picking a folder goes on into it. The last compile's errors and the file's dry run errors are marked on the lines they come from; `]e` and `[e` jump to the next and previous one, wrapping around, and show its message (in the Scratch editor too). The lines changed since git's index are marked beside the line numbers, as gitsigns marks them: a green bar for added lines, a blue one for changed lines, and a red notch where lines were taken out (a file git doesn't track yet is all added; one it ignores, or outside a repository, has no marks). The marks follow your typing, and update when you come back to the page after a `git add` or a commit. `]g` and `[g` jump to the next and previous change, wrapping around, and open its peek, as VS Code's does (a click on a mark opens it too): the lines it took out in a red block above the lines it put in, which are tinted green, with the characters that differ marked in both; it follows your typing and closes on `escape` or when the cursor leaves the change. `guh`, or the peek's **undo**, undoes the change under the cursor, putting its lines back as the index has them (`u` brings the change back; `gu` followed by any other motion still lowercases). The settings page's Vim section changes these keys, and `K` and `gd`. Only the files of the project's actions can be opened and saved. A save is refused when the file changed on disk since the pane loaded it (a save in another editor, a `git checkout`, a formatter): you then choose to reload, overwrite or see the difference. With no unsaved changes, the pane reloads by itself when the file changes. While it has unsaved changes, following the editor waits, and actions of other files can't be selected until you save or drop them. Set `sourceAutosaveMs` (in your user config or `.xf/config.json`, e.g. `1500`; less than 500 acts as 500) to save without `:w`: leaving insert mode, or the editor, or a normal-mode change (`dd`, `p`) starts the countdown, a further change restarts it, and going back into insert mode stops it, so half-typed SQL isn't compiled. Selecting another file's action, following the editor or `q` then saves first. A file changed on disk pauses autosave (the title says so) until `:w` settles it.

**The rail (xf web only).** A thin column of icons on the far left opens, from top to bottom, the file tree, Search, Source Control (with how many files have changed), the open projects (with how many, when more than one) and the terminal (the log, where there is no terminal tab), with the settings' gear at its foot. Each does what its key does, and hovering one names it with that key. The one showing is lit; a click on it again hides it. The column's title names the view it shows (`0 source control`), with its count. A zoomed pane hides the rail. See [ADR 0035](adr/0035-xf-web-has-a-rail-of-icons.md).

**The file tree (xf web only).** `⌘b` (`ctrl+b` on Linux and Windows) shows the project's files in a column on the far left, as VS Code's explorer does, from anywhere, the editors included (on Linux and Windows it takes the key from vim, whose `ctrl+b` pages up); `ctrl+0` gives it the keys. `⇧⌘e` (`ctrl+shift+e` on Linux and Windows), as VS Code's Show Explorer, shows the tree with the open file's row in the middle and gives it the keys, whichever view the column showed; pressed again while the tree has the keys, it gives them back to the editor and the tree stays ([why](adr/0036-xf-web-shows-the-open-file-with-cmd-shift-e.md)). It lists what git does (tracked and untracked files, not ignored ones), marks each with its git status, its compile errors and ● for unsaved changes, and follows files made or removed outside the page. `j`/`k` move, `l` or `enter` opens a folder or a file, `h` closes a folder, `a` makes a file (end the name with `/` for a folder), `r` renames or moves, `m` moves (the same box, with the folder selected to type another; a folder that isn't there is made), `d` moves to the system's trash, `y` copies the absolute path and `Y` the path in the project, `/` filters. A click on a file opens it and leaves the keys in the tree; a double-click gives them to the editor. A right-click shows a menu: New File… on a folder (or the empty space below the files, for the project's root), Copy Path, Copy Relative Path, Rename…, Move… and Delete. Opening an action's file selects its action; any other file (an include, `workflow_settings.yaml`, a `schema.yml`) opens in the source pane on its own, with nothing selected, and `ctrl+^` goes back to the file before. Renaming an action's file renames the action when it is named after its file; the confirmation says how many actions refer to it. See [ADR 0006](adr/0006-xf-web-has-a-file-tree.md).

**Source Control (xf web only).** `ctrl+g` (ctrl on a Mac too) swaps the file tree's column to Source Control, as VS Code's is; `⌘b` swaps back, and either key hides the column when its view already shows. It lists the repository's Merge Changes (files in conflict), Staged Changes, Changes, Stashes and Recent commits, with the commit message box on top, leaving out Merge Changes, Staged Changes and Stashes while they are empty (on a clean tree Changes says *nothing to commit, working tree clean*; its header's *stash* button stashes, as Stashes's does); Changes opens each time Source Control shows, and the other sections stay open or closed as you left them (vim keys, rulers at 50 and 72, `⌘↵` commits, escape twice goes back to the list). With nothing staged, a commit asks whether to stage every change and commit (`y`), as **Commit all** does; on a clean tree both buttons are dimmed. `j`/`k` move, `enter` shows a file's difference in the source pane, `space` stages or unstages (marks a conflict resolved, applies a stash), `a` stages all, `x` discards (a copy of the file goes to the trash first), `c` goes to the message box, `A` amends HEAD (not once it's pushed), `P` pushes, `p` pulls (fast-forward only; on a stash, pops it), `f` fetches, `s` stashes everything, `d` drops a stash, `n` makes a branch (at the commit under the cursor), `y` copies a commit's SHA, `/` filters. A change shows inline, the lines taken out above the lines that replaced them, in the source pane's editor, which edits the file; with `diffStyle` set to `side-by-side` (in the settings, Scratch & source) it shows the index on the left beside it. `t` (outside the editor) flips between the two, and a narrow pane shows inline. A difference opens on its first change. `gsh` stages the change under the cursor wherever the source pane shows git's changes (in a staged file's difference, it unstages it). While a push, pull, sync or fetch runs, its button spins and the status line says so. After any git command, here or in a terminal, the source pane reads its file and git's index again, so a pull shows the new text and a commit clears the change marks. A failed command shows git's last line in red, which opens the git output: every command Source Control ran. git never asks for a password here: use a credential helper or ssh-agent. See [ADR 0007](adr/0007-xf-web-has-source-control.md).

**Merge requests and pipelines (xf web only).** When the branch's push remote is on GitLab or GitHub, the status line shows its merge request (pull request on GitHub) and last pipeline beside the branch: `!42 ●` while the pipeline runs, `!42 ✓` or `!42 ✗` once it ends, `+ MR` when there is none, dimmed when the host can't be reached (a VPN that is off). A click opens Source Control at its merge request region, docked at the bottom below a sash (drag it to resize, click its header to fold it; `tab` jumps between it and git's part), with the title, the target (`→ main`; its tooltip has source → target), a draft pill for a draft (its title's `Draft:` dropped), approvals, unresolved threads, what blocks the merge, and the pipeline's stages and jobs (a trigger job shows the status of the pipeline it started, and opens like a stage to that pipeline's stages and jobs; xf keeps asking while it runs, even once the parent has passed); `o` opens the merge request (on a job, the job), `O` the last pipeline, `m` creates one (it offers to push first, then opens the host's new merge request page), and `enter` opens the row (on a stage or a trigger job, opens or closes it). The palette has Git: create MR, open MR, open last pipeline, copy MR link and refresh MR. xf only reads, with a token of its own: add hosts and tokens in Settings › Git hosting (kept in `tokens.json` beside your config, mode 0600; `read_api` on GitLab, read access to pull requests, actions and checks on GitHub). github.com and gitlab.com need no entry, and `$GITLAB_TOKEN` / `$GITHUB_TOKEN` work there; a self-hosted host needs one. While a pipeline runs xf asks again every `forgePollSeconds` (10 by default, 5 at least), only for projects a window shows. See [ADR 0020](adr/0020-xf-web-shows-the-branchs-merge-request-and-pipeline.md).

**Markdown files (xf web only).** Beside a `.md` file in the source pane, pane 2 shows the file rendered as GitHub would: tables, task lists, code blocks coloured as the SQL pane colours SQL, and the project's images. It follows your typing, unsaved changes and all. Raw HTML in the file is left out. A link to a heading scrolls there, a link to a file of the project opens it in the source pane, and a web link opens in the browser. `autoHidePane2` leaves pane 2 shown beside a Markdown file. See [ADR 0027](adr/0027-xf-web-previews-markdown-in-pane-2.md).

**Python files (xf web only).** A `.py` file in the source pane is checked by [pyrefly](https://pyrefly.org)'s language server, which xf web starts the first time you open one in a project and stops when the project closes: its errors are marked as you type, `K` (or the mouse) shows its hover, `gd` goes to a definition (into a library, such as a venv's `site-packages` or the standard library, it shows the file read-only, and `ctrl+o` comes back), and completion and a call's signature show as you write. Install it with `uv tool install pyrefly` (or into the project's venv); without it, xf web says so once and the file is highlighted only. pyrefly resolves imports with the project root's `.venv/` (or `venv/`) when there is one; *Python: select interpreter* in the palette's commands, or a click on `py:` in the status line, picks another, kept for you in the project's session rather than in a file the team shares. pyrefly reports no type errors without a config, so the first time a project without a `pyrefly.toml` (or `[tool.pyrefly]` in its `pyproject.toml`) shows a Python file, xf web offers to write one at the root, leaving out `target/`, `dbt_packages/`, virtual environments and the like; `n` declines for good, and *Python: create pyrefly config* writes it later. The Settings page shows the project's config file (or a button to create one) and the interpreter under the `pythonLanguageServer` row; set to `off`, it turns it all off. See [ADR 0018](adr/0018-xf-web-checks-python-with-pyrefly.md).

**Formatting SQL (xf web, and `xf lsp`).** *Format: file* in the palette's commands, `:format` (`:fmt`) in the source pane's or Scratch's editor, and *Format File* in the source pane's right-click menu, and a key if you set `vimFormat` (e.g. `<leader>=`), run [sqlfluff](https://sqlfluff.com)'s `format` over the file's SQL; `xf lsp` answers an editor's *format document* the same way. It runs only when you ask: nothing formats on save. The result lands in the editor, unsaved, as one undo step (`u` undoes it), so you read it before `:w`. In a `.sqlx` file it formats the main query and the body of each `pre_operations` and `post_operations` block, each where it sits, and the `config { }` block (in xf itself, no sqlfluff needed: one property to a line, 2-space indent, arrays on one line when they fit in 80 columns, no trailing comma, comments kept, any value that isn't a literal, array or object kept as written); `js { }`, the comments between blocks and the order of blocks stay as they were. Each `${ … }` is hidden from sqlfluff while it runs, so `${when(incremental(), …)}` in a column's place, or `${ref("x")}` inside backticks, needs no templater setting in your `.sqlfluff`. `format` runs only sqlfluff's layout and capitalisation rules, so it never changes what a query means (no added `AS`, no rewritten `GROUP BY`). Dataform only: a dbt model's Jinja isn't hidden, so xf says so and leaves it. It uses your own sqlfluff config (a `.sqlfluff`, `tox.ini`, `setup.cfg` or `pyproject.toml` in the file's folder or above it, up to the project's root), or `sqlfluffConfig` if set; with none, a style built into xf: the Dataform Tools extension's `.sqlfluff` (BigQuery, 2-space indent, leading commas, upper-case keywords and functions, aligned aliases), less the templater lines xf doesn't need, and with identifiers left as written. `sqlfluffConfig` replaces the project's own config rather than adding to it. xf never writes a config into your repo. sqlfluff is found from `sqlfluffBin`, then the project's `.venv/` or `venv/`, then `PATH` (`uv tool install sqlfluff`); without it xf says so and formats only the config block. SQL sqlfluff can't parse is left alone and the message names the line and column in your file, with no compile needed first. See [ADR 0024](adr/0024-xf-formats-sql-with-sqlfluff.md).

**Search in files (xf web only).** `⇧⌘f` (also `ctrl+shift+f`; `ctrl+shift+f` on Linux and Windows) shows Search in the same column, as VS Code's is, from anywhere in the project view, the editors included, with the box focused: on the editor's selection when it has one on one line, else on the last search. `⌘b` hides it and `ctrl+g` swaps to Source Control. It searches the files the tree lists as you type, skipping binary files and files over 2 MB, and stops at 5,000 matches. `alt+c`, `alt+w` and `alt+r` toggle match case, whole word and regular expressions (RE2, with `$1` in a replacement); the `…` shows fields for files to include and exclude (`definitions/**`, `*.md, includes/`). `enter` or `↓` goes to the matches: `j`/`k` show each one in the source pane, `enter` goes there, `h`/`l` close and open a file's matches, `x` dismisses one, `/` goes back to the box. `F4` and `shift+F4` go to the next and previous match from anywhere. The `▸` beside the box shows the replace field: each match then shows what it becomes, `r` replaces the match or file under the cursor, and `⌘⌥↵` (`ctrl+alt+↵`) replaces them all after asking. Matches in the file the source pane shows change in its editor, where `u` undoes them; other files change on disk, and "undo replace" puts back the last replace's files that haven't changed since. A match whose file changed after the search is skipped, not replaced elsewhere. See [ADR 0016](adr/0016-xf-web-searches-files-with-cmd-shift-f.md).

The TUI and xf web each have their own colour theme. The TUI's is `auto`, `light` or `dark`: in `auto` it follows your terminal, drawing plain text in your terminal's own text colour and picking the accents for its background. `>` *View: theme* in the TUI cycles it, saves it to the `theme` key of your user config file and changes every open TUI. xf web has themes of its own: xf Light and xf Dark (its own look), One Dark Pro, Dracula, GitHub Light, Dark and Dark Dimmed, Tokyo Night, Storm and Day, Catppuccin Latte, Frappé, Macchiato and Mocha, Night Owl and Light Owl, Nord, Ayu Light, Mirage and Dark, Monokai Pro Classic and Shades of Purple. Each one colours the whole page, not only the code, with the theme's own palette; the focused pane is the theme's green and what is under way its yellow. The `◐` button, or `>` *View: colour theme*, lists them: moving through the list shows each one, enter keeps it (saved as `webTheme`) and esc goes back. `auto` follows your browser's colour scheme: picking it goes on to ask for the theme to show while the browser is light (`webThemeLight`, xf Light by default) and then the one for dark (`webThemeDark`, xf Dark by default), each previewed as you move; esc on the way keeps what you had. `webTheme` values from before, `light` and `dark`, still mean xf's own. In a project the picker saves for every project, or for this project alone: `tab` switches, and it opens on this project when its `.xf/config.json` already sets a theme. A project's own theme (any of `webTheme`, `webThemeLight`, `webThemeDark` in its `.xf/config.json`) wins over your user config for the keys it sets, shows as `· project` on the `◐` button, and the picker's *inherit* row takes it out again. The TUI's `theme` stays yours alone. See [ADR 0021](adr/0021-xf-web-theme-can-be-a-projects.md). Inside tmux, the TUI draws in true colour when your terminal supports it, as tmux reports, so your terminal's palette doesn't change xf's colours.
