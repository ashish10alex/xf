How “Defer to Prod” Works in xf for Dataform

Dataform lacks native --defer support. xf implements dual-path deferral: zero-cost in-memory AST rewriting for dry runs/diagnostics, and BigQuery Proxy Views for CLI/API execution.

Without Deferral (Native Dataform Pain)

In isolated dev datasets (dev_ashish.*), running or validating a leaf model fails with “Not found: Table dev_ashish.raw_events”. You are forced to waste time and BigQuery compute building all upstream tables in dev.

With xf Defer to Prod (ADR 0031)

Upstream models missing in dev are transparently redirected to their prod targets (prod_dw.*). Dev builds only your changed models, with zero DDL cost during dry-runs and automated lightweight proxy views during execution.

Path A: Dry-Run & Editor Diagnostics

Zero-DDL In-Memory SQL Rewriting

Dataform produces backtick-quoted table targets: `dev_project.dev_schema.table`. When xf dry-runs a model or validates it for Neovim/VS Code LSP, deferral.Rewrite() swaps missing dev references with prod targets in-memory before sending the query to BigQuery with dryRun: true.

Standard Dataform Compiled SQL (Dev) FAILS BQ DRY-RUN 
-- Target: dev_ashish.fct_sales
SELECT 
  s.order_id,
  s.amount,
  u.customer_name
FROM 
  `dev_proj.dev_ashish.stg_orders` s
JOIN 
  `dev_proj.dev_ashish.dim_customers` u
  ON s.customer_id = u.id;
BigQuery Error: Not found: Table dev_proj:dev_ashish.stg_orders was not found in location US
xf Rewritten SQL via deferral.Rewrite() SUCCEEDS (0 BYTES SCAN) 
-- Target: dev_ashish.fct_sales (Rewritten)
SELECT 
  s.order_id,
  s.amount,
  u.customer_name
FROM 
  `prod_proj.analytics.stg_orders` s
JOIN 
  `dev_proj.dev_ashish.dim_customers` u
  ON s.customer_id = u.id;
Valid Dry Run: Evaluated against prod schemas. Line offsets preserved 1:1 for precise diagnostic reporting.
1

Line Preserving

Newlines and whitespace are untouched. Any BigQuery syntax or column error points directly to the correct source line in your editor.

2

Exact Backtick Replacement

Dataform outputs fully qualified `db.schema.name`. xf replaces only matching backtick pairs to avoid corrupting custom string literals.

3

Cached Lookup Index

BigQuery table existence is cached for 2 minutes (lookupTTL = 2 * time.Minute), so typing and saving creates zero BigQuery API congestion.

Path B: CLI & Cloud Dataform Execution

BigQuery Proxy Views in Dev Dataset

When you trigger a real run (xf run or Cloud Dataform API), Dataform compiles its own execution graph requiring tables to exist at their dev targets. Before running, xf invokes EnsureProxies() to create lightweight 1-line views in dev pointing to prod.

STEP 1

Pre-Run Reconciliation

xf identifies all upstream dependencies in the execution set. It checks dev: if a table is already built in dev, it is left untouched. If missing, it checks prod existence and permissions.

STEP 2

Proxy View Creation with Shared Extension Label

For every deferred candidate, xf creates a BigQuery View in your dev dataset:

-- View created in dev_ashish:
CREATE OR REPLACE VIEW `dev_proj.dev_ashish.stg_orders`
OPTIONS(
  labels = [("dataform_tools_proxy", "true")],
  description = "Defer to prod proxy for prod_proj.analytics.stg_orders, created by xf"
) AS
SELECT * FROM `prod_proj.analytics.stg_orders`;

☆ Interoperability: Uses the exact label (dataform_tools_proxy) as the official Google Dataform VS Code extension, so either tool can detect, reuse, or purge each other's proxies!

STEP 3

Standard Dataform Runner Execution

Dataform executes the pipeline using its standard CLI or Cloud API. Because the dev targets exist as views, Dataform compiles cleanly and queries prod data via the dev views.

STEP 4

Replacement & Clean Up

When you eventually build stg_orders in dev, Dataform's CREATE OR REPLACE TABLE overwrites the proxy view with the real dev table. Alternatively, run removeProxies from the palette.

Edge Cases & Safety Governance

Safety Verification & Pre-Run Dialogs

Blindly deferring can cause subtle data corruption if upstream logic changed on your branch. xf runs strict pre-flight checks before executing any deferred job.

Scenario / Edge Case Detection Mechanism Risk xf Mitigation / Dialog Choice
Stale Deferral Upstream model ∈ ChangedActions Prod data does not match the branch's new code logic. Grills user with choices:
• Build changed first: adds upstream models to dev run
• Run with deps: full upstream cascade
• Run anyway: accepts stale prod output
